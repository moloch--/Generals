## 2026-10-24: Recover crash evidence and improve Windows diagnostics

Preserved the two October 22 release-crash reports, the unfinished last replay,
the original executable and symbols, and local system evidence under
`logs/crash-recovery-2026-10-24/`. Both reports contain the generic
`GameEngine::update` exception message; their four dump files are empty.
These artifacts do not identify the original failing operation.

Reproduced a separate diagnostics bug: after the minidumper preloads DbgHelp,
the stack-report initializer returns success without initializing a symbol
session. A focused x86 probe consequently could not resolve its own executable
module. Both games now use shared, idempotent process-symbol initialization
with a loader reference that survives minidumper shutdown. Failed dump writes
also retain the operation and Windows error in a text sidecar in Release builds;
paired sidecars count as one capture in the existing retention allowance.
Standalone failure reports are also bounded, and failed sidecar deletions are
retried on the next launch.

The update-loop catch now preserves engine `ErrorCode` names and hexadecimal
values, or `std::exception::what()`, in a fixed stack buffer. A failed replay
cleanup is recorded separately and cannot replace the original exception.
This improves the crash reason; it does not recover the original throw-site
registers or stack after unwinding.

Windows release-crash reports also capture process memory, system memory,
free virtual address space, and its largest free region before dump generation.
The platform helper uses fixed storage and OS queries. These counters are
evidence for a later diagnosis, not an automatic out-of-memory diagnosis.

Added opt-in diagnostics tests (`RTS_BUILD_DIAGNOSTICS_TESTS=ON`). All four focused
Release/x86 CTest cases pass: symbol-session lifetime, unavailable dump-entry
reporting, a real minidump's exception/thread/context, typed exception details,
nested cleanup failure, bounded formatting, and memory counters responding to
a real 32 MiB virtual-address reservation and release, and retention of paired
dumps, standalone reports, and initially locked reports. The production DbgHelp wrapper
also produced a valid dump in an isolated baseline probe, so the original
zero-byte dump failure has not been reproduced. These diagnostic fixes are not
evidence that the two online gameplay crashes are fixed. The existing endpoint and WWMath
determinism tests also passed with the live
`tls://multiplayer.generals.network:29900` TLS handshake enabled.

Both Windows entrypoints now report an escaped startup, replay, or shutdown
exception to stderr and return failure instead of silently swallowing it.
Rebuilt the Windows game and personal SFX through the automated source builder.
The preserved baseline and rebuilt engine both completed rendered playback of
the recovered recording plus a 30-second diagnostic tail at frame 27,269,
without a CRC mismatch, and exited zero. All original replay bytes and CRCs
were retained. Headless baseline playback diverged near frame 8,718, so it is
not evidence of equivalent rendered playback or a reproduction of the crash.

A two-client baseline Online AI soak on Hostile Dawn recorded 375 matching
CRC rounds through 20:50 of shared simulation. It used four Hard Armies and
light human build input; the human bases were eliminated and observation
continued. Both processes exited zero through the UI. This was a different
workload from the recovered match and did not reproduce its crash.

A deliberately injected release crash in the rebuilt engine wrote valid
263 KB minimal and 445 MB full dumps, matching private symbols, the controlled
reason, and memory counters. Both dumps contain the expected synthetic
DebugBreak context. This tests the reporting path, not the original failure.
The completed native-launch checks used isolated profiles with verified registry restoration.

The exact final SFX hosted two preserved baseline clients through the public
Online service on Hostile Dawn, with three Hard Armies across three teams.
The pre-exit snapshot reached frame 36,114 (20:03.8) on all three peers, with
361 matching three-peer CRC rounds and identical command records. This included
light manual construction, infantry/vehicle production, movement, and sustained
AI combat. No crash or desync was observed. All clients closed through the UI;
the launcher and both directly launched guests returned zero, and the exact
previous profile setting was restored. This validates the observed mixed-build
workload, not the unreproduced October failure. Full results and limitations are
in `docs/WORKDIR/reports/2026-10-24-online-crash-diagnostics.md`.

Full verification of the final automated-build SFX passed for the embedded
payload and every extracted file. The separate desktop delivery is
`GeneralsXZH-online-diagnostics-20261024.exe` (1,769,178,112 bytes), SHA-256
`6499fdb4306230f2ae7dca64cc5bdda2c4116b3ad95e600bbb316521c9d44077`.
Its exact executable and PDB are preserved under
`logs/crash-recovery-2026-10-24/final-binary-and-symbols/`.

An early debugger-parent baseline launch did not use the intended isolated

## 2026-10-10: Implement downloadable runtimes and local assembly

Published [runtime-v0.1.0](https://github.com/moloch--/Generals/releases/tag/runtime-v0.1.0)
from `bfc4c6aa65132da09abacc8a10c2760e88973d6f`. Linux AMD64, macOS ARM64, and
Windows x86 all passed native engine builds, runtime validation, and real
installer assembly/verification with synthetic retail fixtures in the
[tagged workflow](https://github.com/moloch--/Generals/actions/runs/38074499258).
Downloaded all seven public assets and checked their hashes and identities.
A fresh-cache Windows build then fetched the published runtime through the
normal public resolver, assembled its SFX, and passed full `--sfx-verify`.

The final public metadata check found GitHub automatically choosing the runtime
as the repository's latest release despite `--latest=false`. Added a small
Actions maintenance job to explicitly pin the newest stable builder release,
preserving the separate builder and runtime channels without changing assets.
Its first run exposed that `gh api --slurp` cannot combine with `--jq`; moved
the complete paginated response through standalone `jq` before selecting a tag.

The first Windows CI job failed while vcpkg tried to lazy-fetch historical
port blobs from a partial clone. Changed CI to acquire the complete vcpkg
object history before dependency setup. Subsequent main and tagged runs passed
on every platform. Added native end-to-end assembly tests, including the macOS
app wrapper, plus the opt-in public-download check. The guide records actual
release availability and the current headless command; builder release
`v0.0.6` predates prebuilt mode.

Implemented PLAN-024 steps 1 and 2. The CLI and desktop tool now offer source
or prebuilt mode; source stays the default. Prebuilt mode resolves a published
runtime, verifies and caches it, combines it with owned assets in private
staging, and packages/verifies the personal output. It skips the engine compiler,
Git checkout, and dependency build. Go remains required for SFX packaging, and
macOS still compiles the small progress helper with Command Line Tools.

Added native GitHub Actions lanes for Linux AMD64, macOS ARM64, and Windows x86
(inside an AMD64 launcher). Runtime tags publish a complete, verified release
through a draft; ordinary builds retain temporary CI artifacts. Each archive
contains a normalized engine, dependencies/notices, measured platform metadata,
and the matching minimal packaging kit. Retail files and Windows Bink/Miles
DLLs are excluded from distribution and remain local inputs.

Validated an actual Windows runtime export and offline local assembly using
synthetic retail fixtures. The real Go packer produced an SFX whose full
`--sfx-verify` passed. Root, desktop, and SFX Go suites passed, as did root
`go vet`, 70 frontend tests, workflow/script syntax checks, and Linux/macOS
cross-builds of the builder and extracted-kit launcher. Regression tests cover
corrupt/unsafe archives, interruption, concurrent downloads, asset preservation,
directory casing, retail DLL imports, and late output failures with rollback.

The first release requires Linux glibc 2.38+, macOS 15+, or Windows 10+.
Native builds and packaging tests do not establish retail gameplay or replay
compatibility; those checks had not been run at publication. Full frontend
production compilation also needs the licensed HeroUI Pro artifacts unavailable
in this session. Source builds remain available and stay the default.

Desktop tests exposed Windows home/cache fixture isolation bugs. Updated tests
to isolate USERPROFILE/LOCALAPPDATA as well as HOME/XDG_CACHE_HOME. Earlier runs
left a tiny test checkout in the default source path and a cache marker;
automatic approval review blocked their removal. Disposable default cache
subdirectories were also exercised before isolation was corrected; prior cache
contents were not inventoried. The project checkout and retail assets were
unaffected.

The live service requires game compatibility generation 2. With approval,
integrated the deterministic client changes from
`feat/online-cross-platform-determinism` (`ea9a5c67`, `c3056f7c`) while retaining
the newer build tooling. This pins GameMath, routes simulation math through
deterministic wrappers, fixes reduction ordering, and preserves relay state
through the staging-to-game handoff.

Testing under the actual simulation floating-point mode found a Windows x86
precision bug: MSVC can emit x87 double-return arithmetic even with SSE2.
The retail 24-bit x87 mode truncated deterministic double results. Generation
2 now uses 53-bit precision; legacy mode retains 24-bit precision. Both games
and the regression test share the reset helper in the platform layer. The
test disturbs rounding first and uses runtime operands so constant folding
cannot conceal the regression. MinGW x86 deterministic builds also request
SSE2 scalar arithmetic. The native Online and deterministic math tests pass.

Two temporary QA accounts logged in through the native game UI, created and
joined a password-protected match on the public service, and loaded Alpine
Assault. Both clients accepted unit movement and building construction while
the service reported an active two-player game. The match finished normally
after 285 seconds; both finalized replays contain 8,415 frames, no desync,
no early quit, and no disconnected player slots. The service then reported
zero active games and zero open lobbies. After the text fixes, repeated login,
protected joining, map load, and movement with the exact final game binary;
that match finalized at 173 seconds / 4,895 frames with the same clean flags.
The final UI also displayed all four room names and unavailable statistics
correctly. This exercises two Windows x86 clients on this host;
Linux/macOS interoperability and legacy replay compatibility are not yet
validated.
Both clients logged out afterward; the public snapshot returned zero online
players, lobbies, games, and queued players. Removed their generated login
profiles from game user data. No backend changes were required.

Also corrected Online room names being treated as legacy translation keys,
unavailable faction statistics showing literal format placeholders, and the
UTF-8 conversion helper's buffer-size and POSIX locale dependencies. A shared
platform decoder now handles UTF-16/UTF-32 output and rejects malformed input;
focused tests cover ASCII, multibyte, supplementary, line-break, and invalid
input cases.
Legacy room localization is retained when the custom Online service is not
configured.
